# Plan: Template-Driven Tailored Resumes from the Content Library
**Started:** 2026-10-01
**Status:** 🔄 In Progress

## Goal
The user maintains `~/.applypilot/content_library.md`, a bank of raw facts per project grouped under
roles: 4 roles and about 19 projects, each with Context/Scope/Tools/Outcome/Angles. Today
`tailor_from_content_library()` asks the LLM for JSON that always includes `title`, `summary`, and `projects`.
`assemble_resume_text()` flattens that JSON to text, then `pdf.parse_resume()` re-parses the text and
`pdf.build_html()` renders it in a **generic** layout. The user's real resume (`personal/resume.txt`,
`~/.applypilot/resume.pdf`) looks different:
- Header: name, then a contact line separated by `▫` (city, email, phone, LinkedIn, GitHub)
- **WORK EXPERIENCE**: `<Title> at <Company>` with right-aligned dates, an optional one-line company tagline, and `•` bullets
- **EDUCATION**: fixed text, copied verbatim from the base resume
- **SKILLS**: `Category: items` rows
- No summary, no projects section, no title line

After this plan, each tailored resume uses the user's resume as the template (same sections, order,
typography, fixed blocks). Only the variable parts are generated from the content library: bullets per
role, which roles and internships appear, and skill ordering. Output goes straight from validated JSON
to HTML to PDF, with no text round-trip, and every bullet can be traced back to the library projects it came from.

## Success Criteria
1. `applypilot template preview` renders `~/.applypilot/resume_template.html` filled with the **base resume's own content** to `~/.applypilot/template_preview.pdf`. That PDF is one page and has the same section order and header/contact formatting as `resume.pdf`. The user signs off on a side-by-side check, recorded in Historical Record.
2. `applypilot run tailor --source content-library --limit 3` produces 3 PDFs. Each one is one page (`render_pdf(...)["overflow"] is False`), and each has a sibling `.json` listing `project_ids` used per bullet.
3. Education and the header are byte-identical across all tailored resumes (`pytest tests/test_resume_template.py -k fixed_blocks`).
4. Every number in a generated bullet appears in the source project's facts (`pytest tests/test_resume_template.py -k provenance`).
5. `--source content-library` is the default when `content_library.md` exists (`applypilot run --help` shows it).
6. `pytest tests/ -q` passes.

### Task 1: Structured tailored-resume model
**Runs:** cloud
**Files:** `src/applypilot/scoring/resume_model.py` (new), `tests/test_resume_template.py` (new)
**What:** Define typed dataclasses matching the user's resume, not the generic one:
```python
@dataclass
class Bullet:
    text: str
    project_ids: list[str]          # slugs of content-library projects the facts came from

@dataclass

    role_key: str                   # e.g. "air-associate", matches a content-library role

    company: str
    dates: str
    tagline: str | None
    bullets: list[Bullet]

    roles: list[RoleEntry]
    skills: dict[str, str]          # ordered category -> items
    dropped_roles: list[str]
```

`ValueError` on unknown `role_key`/`project_ids`. Also add `.to_json() -> str`. Add a stable `slug` to
`content_library.Project` (kebab-case of the heading, deduplicated with role key) if it doesn't already exist.

## Key Design Decisions
1. Use an HTML/Jinja template rendered by the existing Playwright `render_pdf` instead of DOCX. That reuses the working PDF and overflow pipeline, and avoids LibreOffice.
2. Code supplies the header and education, never the LLM. Those blocks are fixed facts, and generating them only creates chances for errors.
3. Bullets carry `project_ids` so each claim can be traced to library facts and checked mechanically, instead of relying only on an LLM judge.
4. Slot ranges come from the base resume so the tailored resume has the same shape and density as the one the user already likes, and fits on one page.
5. Put the library first in the system prompt so the prefix is identical across jobs and eligible for Gemini implicit caching.
6. Keep the legacy `--source resume` path untouched, so this change can't break existing behavior.
